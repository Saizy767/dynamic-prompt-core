# prompt-loop

Исследовательский пайплайн для итеративной оптимизации системного промпта
бинарного классификатора на базе маленькой языковой модели (класс Tiny, до 3B
параметров).

## Назначение

Цель — не ручное написание промпта, а построение цикла, в котором системный
промпт эволюционирует на основе анализа ошибок и reasoning модели. Каждый шаг
цикла логируется, изменения можно откатить.

## Концепция

Системный промпт рассматривается не как текст, а как контракт между
разработчиком и моделью. Он состоит из фиксированных семантических слоёв:

- роль
- задача
- правила
- контракт вывода
- fallback

Слои упорядочены по стабильности — от неизменяемых к динамическим. Это
сохраняет prefix-кэш на inference-сервере.

Модель работает при `temperature=0` и возвращает структурированный вывод:

- `decision` — 0 или 1
- `reasoning` — список коротких пунктов

Reasoning маленькой модели шумный и является пост-хок рационализацией. Поэтому
он используется не поштучно, а через частотный анализ по группам: правильные
`decision` против неправильных.

Цикл оптимизации:

1. Прогон на dev-выборке.
2. Сбор метрик и статистики по reasoning.
3. Предложение изменений в промпт.
4. Ручное ревью.
5. Применение.
6. Следующий прогон.

Изменения применяются только после подтверждения человеком. Минимум на первых
10 итерациях — обязательно: датасет меньше 200 примеров, автоматическая
оптимизация переобучится.

## Архитектура

Компоненты связаны однонаправленно: датасет и промпт поступают в runner, runner
вызывает клиент к модели, результаты разбираются парсером, метрики и анализатор
reasoning работают поверх результатов, всё фиксируется в логе изменений.
Оркестратор последовательно вызывает компоненты для первого запуска.

## Компоненты

### Датасет

Таблица с колонками `text` и `label` (0/1). Разбиение на `dev`, `holdout`,
`ambiguous`. При размере меньше 200 примеров — 5-fold cross-validation вместо
жёсткого разбиения.

Артефакт: `jsonl` или `parquet` с полями `id`, `text`, `label`, `split`,
`notes`.

### Клиент к модели

Обёртка над `AsyncOpenAI`. Единый интерфейс:

```
classify(text, system_prompt) -> raw_response
```

Поддержка llama.cpp и vLLM через конфиг, а не через код. Параметры:
`temperature=0`, `top_p=1`, ограниченный `max_tokens`, retry с exponential
backoff, таймауты. Batch-режим.

Логирование каждого запроса: `timestamp`, `model name`, хэш промпта, хэш текста,
`raw_response`, `latency`.

### Схема вывода и парсер

Pydantic-схема:

- `reasoning: list[str]`
- `confidence: int`
- `decision: int`

Жёсткие лимиты: `reasoning` не более 5 элементов, каждый до 20 слов;
`confidence` в диапазоне 0–100; `decision` строго 0 или 1.

Парсер чинит «почти-JSON»: обрезанные скобки, markdown-обёртку, лишний текст
вокруг. Провал парсинга логируется отдельно от ошибки классификации.

### Базовый системный промпт v0

Пять слоёв: роль, задача, правила (3–5 пунктов), контракт вывода, fallback.
Хранится как артефакт с версией и хэшем. Рендерится в текст через простой
шаблонизатор. Цель v0 — не идеальность, а наличие baseline.

### Runner

Прогон датасета через модель. Итерация по `dev` или фолдам. Чекпоинты для
продолжения с места обрыва. Сборка результатов в таблицу: `id`, `text`,
`true_label`, `predicted_decision`, `reasoning`, `confidence`, `parse_status`,
`raw_response`. Сохранение в файл с `timestamp` и версией промпта.

### Метрики

Accuracy, precision/recall/F1 по каждому классу, confusion matrix, количество
ошибок парсинга, распределение предсказаний, разбивка по группам текстов.
Считаются автоматически после каждого прогона.

### Анализатор reasoning

Токенизация, разделение на группы (правильные/неправильные `decision`),
подсчёт частот, ранжирование по отношению частот, фильтрация стоп-слов, топ-30
на группу. Анализ устойчивости reasoning при перестановке классов. На первом
этапе не оптимизирует промпт — только собирает статистику.

### Лог изменений

Журнал экспериментов: версия промпта, полный текст, хэш, дата, причина
изменения, ссылка на прогон и метрики, список примеров, изменивших `decision`.
Формат — `jsonl` или SQLite.

### Оркестратор

Один сценарий первого запуска: загрузить датасет → загрузить промпт v0 →
прогнать по `dev` → посчитать метрики → собрать статистику по reasoning →
сохранить в лог → вывести отчёт.

## Пайплайн первого этапа (baseline)

Никакой автоматической оптимизации. Только фиксация точки отсчёта: цифры по
метрикам и материал для первой ручной правки промпта.

Первый запуск считается успешным, если:

- модель отвечает
- парсер не падает
- метрики считаются
- лог пишется

### Smoke-тесты до первого запуска

- ответ модели на промпт
- парсер на сыром выводе
- метрики на игрушечных 5 записях
- запись и чтение лога
- загрузка и разбиение датасета

## Границы первого этапа

Вне скоупа:

- автоматическая оптимизация промпта
- teacher-модель для генерации reasoning
- UI
- многоуровневые абстракции «на будущее»
- тонкая настройка промпта

## План развития

- **Этап 2** — архетипы промпта для других классов моделей (Small, Mid, Large).
- **Этап 3** — автоматическое предложение изменений с ручным подтверждением.
- **Этап 4** — teacher-модель для генерации качественного reasoning.
- **Этап 5** — перенос результатов на другие задачи.

## Требования

- Python 3.11+
- AsyncOpenAI
- pydantic v2
- доступ к llama.cpp или vLLM серверу по OpenAI-совместимому API
